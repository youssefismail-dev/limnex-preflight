# Evaluation report, 2026-11-05: Limnex Preflight on 63 fresh, ordinary Hugging Face repositories

Scanner under test: `limnex_preflight` 0.1.0 as it stood on 2026-11-05, before the public release, plus the two fixes made in this
round (section 7). Environment: Linux, Python 3.13.16 (Preflight, 4 cores, no GPU), Python 3.12 for the two other tools,
`picklescan` 1.0.5, ProtectAI `modelscan` 0.8.8 with `tensorflow` 2.20 and `h5py` 3.16. Sampling rule: `evaluation/HELDOUT_V2.md`,
committed (in the private development history) **before** the first model file was downloaded; its "Deviations" section lists D1-D6.

**This is a benign-only, held-out measurement. It says nothing about real malicious models.** Hugging Face's own scanners
filtered the draw (section 2.1), and no malicious or flagged file was downloaded.

**This public version gives totals only.** The per-repository rows (which finding is in which repository, under a
pseudonym) and the per-finding labels are kept in the private development repository: with 60 repositories drawn by
a published rule, one such row could point at one repository's finding.

## 2. Fresh held-out set (task 2)

### 2.1 How the sample was drawn

Rule (committed before any download): seed `20261105`; Hugging Face model listing, `sort=downloads`, six format strata
(`pytorch` pickles, `safetensors`, `gguf`, `onnx`, `keras`, `sklearn`); created in the last 12 months; >= 100 downloads in 30
days; not gated/private/disabled; **not one of the repositories of README sections 2-5** (and not the 7 pseudonymised ones);
**never a repository on which Hugging Face's own scan raised a flag**; download cap 1.0 GB per repository, 6 format files;
text files up to 5 MB. Sorted by id, shuffled with the seed, walked until 10 accepted per stratum. Real ids are in a private
scratch file; this public version names no repository and no pseudonym.

Draw statistics (how many candidates there were, and why some were not used):

| stratum | listed | metadata-eligible | with a format file | excluded (already used in README sections 2-5) | refused for size | **refused because Hugging Face flags the repo** | accepted |
|---|---|---|---|---|---|---|---|
| pickle (`pytorch` filter) | 3000 | 251 | 47 | 2 | 3 | 1 | 10 |
| safetensors | 800 | 253 | 249 | 3 | 27 | 1 | 10 |
| gguf | 300 | 250 | 248 | 2 | 0 | 0 | 10 |
| onnx | 1000 | 279 | 274 | 3 | 0 | 1 | 10 |
| keras | 5000 | 116 | 111 | 4 | 0 | **7** | 10 |
| joblib/sklearn | 1201 | 742 (no download floor, D2) | 586 | 0 | 0 | **32** | 10 |

Two things this table says about the sample:

* **Selection bias towards "clean as far as Hugging Face can tell".** In the joblib/sklearn stratum 32 of the 42 repositories
  walked (76%) carried a Hugging Face security flag and were never downloaded; in the keras stratum 7 of 17 (41%). The accepted
  repositories are the unflagged remainder. That is what "no malicious samples" required, but it means this stratum is not
  representative of all sklearn uploads.
* **Two deviations before any download (D1, D2):** the listing depth in the rule was too shallow (only 19 pickle and 4 sklearn
  candidates in 400 listings), and the sklearn tag has only one recent repository with >= 100 downloads in 30 days, so stratum 6
  has no download floor (its repositories are less used than the others). Both were decided from pool *counts* only, written
  into `HELDOUT_V2.md`, and committed before the first download.

## 3. Comparison with picklescan and ProtectAI modelscan (task 3)

Both tools were run on the same files before deletion, once per directory (for timing) and once per pickle-bearing file (for
verdicts). 67 files qualify (11 PyTorch zips, 30 `.keras`, 26 joblib/pickle). Their option sets are the defaults;
ProtectAI `modelscan` had its TensorFlow and h5py extras (D4).

67 files; each tool was run on each file separately. `review` = Preflight's MEDIUM review tier (not HIGH). `error` = the tool could not parse the file; `not supported` = the tool skipped it.

| Preflight | picklescan | ProtectAI modelscan | files |
|---|---|---|---|
| clean | not supported | clean | 26 |
| clean | clean | clean | 23 |
| clean | error | error | 12 |
| clean | clean | error | 4 |

| tool | flagged | review | clean | error | not supported |

### 3.2 Every disagreement, explained

| files | what happened | explanation |
|---|---|---|
| 26 | Preflight clean, picklescan *not supported*, modelscan clean | `.keras` archives in which picklescan finds no pickle member and reports 0 files scanned (correct: there is nothing it handles); modelscan's Keras scanner accepts them and finds nothing; Preflight reads the archive members and JSON. (I inferred the Keras 3 layout from those two behaviours; the files were deleted and not opened by hand.) |
| 12 | Preflight clean, picklescan *error*, modelscan *error* | **10 are joblib / scikit-learn pickles with inline NumPy arrays** (5 `.joblib`, 5 `.pkl`): picklescan stops with `opcode unknown at position N` (raw array bytes sit between opcodes) and modelscan fails with `PICKLE_GENOPS` / `MODEL_SCAN`. A payload after the first inline array would be invisible to both. Preflight walks past the arrays (carving). This is a **real coverage difference in Preflight's favour** on a format scikit-learn users publish; it is not a detection result (no malicious file was involved). **2 are `.keras` files that are really PyTorch-layout zips** (`<name>/data.pkl`): picklescan warns it could not parse one member, modelscan says "Unable to scan .keras file". |
| 4 | Preflight clean, picklescan clean, modelscan *error* | the same PyTorch-layout `.keras` files in two other variants (picklescan scans `data.pkl`: clean; modelscan's pickle scanner also finds nothing but its Keras scanner errors), one tiny `.joblib` on which modelscan's pickle scanner crashes (`argument of type 'NoneType' is not iterable`), and one `.pkl`. |
| 1 | Preflight clean, picklescan *error*, modelscan clean | a 3.4 MB joblib pickle with inline arrays: picklescan cannot parse it past byte 948; modelscan and Preflight can. |
| 1 | **Preflight review (2 MEDIUM findings), picklescan *not supported*, modelscan CRITICAL** | The one interesting file (a 19 MB `.pkl`). Reading only the opcode and class names: it is a **standard Keras 3 pickle**. It calls `getattr(keras.src.models.functional.Functional, '_unpickle_model')` on an in-memory `.keras` archive. Preflight's review tier asks a human to look (unknown `getattr` name plus a call on a computed callable): MEDIUM, both findings labelled `false`. modelscan calls the same thing `Use of unsafe operator 'getattr' from module 'builtins'`, **CRITICAL** (it flags every `getattr`; README section 3 says the same about YOLO checkpoints). picklescan reported `Scanned files: 0`: the pickle *ends* in a valid zip archive (the embedded `.keras` bytes), picklescan took the whole file for a zip, opened its members, found no pickle among them, and never read the outer pickle. I did not test whether that can be abused and built no sample; it is an observation about the other tool, for its maintainers (privately). |

**Reading the comparison fairly:** on this set Preflight and the two tools agree wherever all of them can parse the file (23 files, all
clean). Preflight parses more of the joblib files than either tool, which matters because a clean verdict from a tool that
silently cannot read the file is not a verdict. Preflight's weak spot shown here is the review tier on a popular, legitimate Keras
pickle shape (one file, MEDIUM: it blocks at the default `--fail-on medium` until someone looks). The corresponding
allow-list entry is a design decision left open (section 7.3), not a bug. There is no true-positive comparison, because there is no true positive.

### 3.3 Cost

picklescan: 5.9 s and 27 MB peak for the 60 main repositories; Preflight: 84.9 s and 222 MB; ProtectAI modelscan with TensorFlow:
142.4 s and 592 MB. Preflight reads many more kinds of files (text, ONNX, GGUF, safetensors headers, archives), so the comparison is
cost per file kind, not a ranking.

The three largest files of the draw: two multi-GB safetensors files and one GGUF (the stress stratum, section 2.1; each 3-8 GB,
downloaded alone, scanned, deleted).

|---|---|---|---|---|---|---|
| stress file 1 | safetensors | 4.7 | 0.186 | 52.8 | 5.2 | 0 |
| stress file 2 | safetensors | 6.2 | 0.27 | 53.2 | 5.2 | 0 |
| stress file 3 | gguf | 4.1 | 1.101 | 92.7 | 12.5 | 0 |

Deep mode (`--deep`, reads every payload byte) on the same files:

| file | file GB | seconds | MB/s | peak RSS (MB) | bytes read (MB) |
|---|---|---|---|---|---|
| stress file 1 | 4.7 | 157.73 | 30.0 | 196.7 | 4300.2 |
| stress file 2 | 6.2 | 157.969 | 38.9 | 197.2 | 4300.2 |
| stress file 3 | 4.1 | 144.827 | 28.2 | 199.7 | 4092.5 |

**Streamed, never loaded:** with default options Preflight reads 5.2 MB through `read(2)` (the interpreter and package
start-up plus the header) and uses 53 MB of memory on a 4.7 and a 6.2 GB file, and 93 MB for the 4.1 GB GGUF
(the metadata of a 4 GB GGUF is parsed, 12.5 MB read). With `--deep`, which reads every payload byte, memory stays at ~200 MB
while bytes read equal the payload up to the cap (the deep table above), i.e. the file is consumed in 16 MB windows with a
small overlap, never in one piece. The runs happened before fix 2; the repeat after the fix is in section 7.2.

**What the stress run found:** both multi-GB safetensors files read **exactly 4300.2 MB** in deep mode although they are 4.7 and 6.2
GB. `scan_stream_deep` had a hard 4 GiB per-payload cap and stopped there without any note: a `--deep` scan of a 6 GB model
reported "complete, no findings" after reading 70% of it. That contradicts the project's own rule that partial scans are
reported. Fixed test-first (section 7.2).

## 5. Public GitHub repositories (task 5)

**Not executed. There are no results for this task.** The rule was written and committed before anything was fetched
(`evaluation/GITHUB_V1.md`) and a driver exists (`evaluation/github_v1.py`), but the environment it ran in could
reach only one repository: every request for a third-party repository's tree returned HTTP 403, so the round stopped
there. `github_v1.py` is **untested beyond its search stage**; the clone and
scan path has never run.

Disclosure: before that limit was noticed, three read-only calls outside it were made, none of which read repository
contents: two uses of the GitHub search API (a connectivity probe printing 3 repository names, and the draw's 9 search
calls, whose results were not saved or used) and one `git ls-remote` on a public sample repository. This is also recorded
in `GITHUB_V1.md` (D1).

Running it needs the two commands in `GITHUB_V1.md` on a machine with ordinary GitHub access. The expected finding there is the opposite of Hugging
Face: committed notebooks and configs are where real credentials are most likely, so every provider-token-shaped hit should be
disclosed privately to its owner and never published.

## 6. Honest limits of this round

* **Benign only, Hub-filtered.** The draw refuses anything Hugging Face flags. Nothing here measures detection of real attacks.
* **One labeller**, an AI assistant, working from masked evidence; `unclear` counts against the scanner. A different labeller could
  move individual labels (for example, treat the corpus e-mail addresses as `intended`).
* **Small samples.** 19 labelled findings, 60 repositories, 10 per format; the intervals above are wide. Findings cluster in files.
* **Popular-recent bias** (sorted by downloads), a 1 GB per-repository cap, no `.h5` Keras file, joblib repositories that are
  unpopular and Hub-clean by construction.
* **The list cannot be redrawn exactly** (the Hub listing changes daily); the seed and code reproduce the draw against a stored
  listing, which is kept privately together with the real ids.
* **LOW findings were not labelled**, apart from the one class that dominated them (167 of 177).
* The scan and labels use the 2026-11-05 version; the fixes of section 7 were validated on the affected real files only (re-scanning the
  other 61 repositories after them was not done; fingerprints of every other finding are unchanged by construction, see 7.1).

## 7. Bugs found and fixed (each: failing test first, own commit)

### 7.1 `hostname-field` matched the PyTorch exporter's graph labels

* Evidence: 167 of 177 LOW findings, two ONNX files from `torch.onnx.export`, key `pkg.torch.onnx.original_node_name`, masked values
  such as `p********` (node names like parameter and layer names). The rule `_HOSTNAME_KEYS` matches any key ENDING in `node_name`.
* Test first: `tests/test_exporter_metadata.py` (strict xfail, fails with `['hostname-field'] == []`); a control test
  proves a real `node_name` / `host_name` key is still reported.
* Fix: keys under `pkg.torch.onnx.` are exporter labels, not host-name fields.
* On the two real files: 130 -> 0 and 37 -> 0 `hostname-field` LOW findings; every other finding on those two repositories
  is identical.

### 7.2 `--deep` stopped silently at 4 GiB

* Evidence: section 4. Test first (strict xfail): with the cap lowered to one read window, a 48 MB payload produced
  `notes=[]`; a control payload under the cap produces no note.
* Fix: when the cap is reached and data remains, the scan adds a `skipped` note ("--deep reads at most 4096 MB of one
  payload; the rest was not scanned"), so `--fail-on-incomplete` and the Action's summary see it.
* On the real 6.15 GB file after the fix: still 4300 MB read, 197 MB peak RSS, and now the note is present
  (`safetensors tensor data: --deep reads at most 4096 MB of one payload; the rest was not scanned`). The cap itself was not
  changed; whether 4 GiB is the right cap is a separate decision.
* My first version of this test used a cap smaller than the 16 MB read window, so it failed for the wrong reason and would have
  failed after the fix too. I noticed because the "fix" commit's test still failed; both commits were rewritten before pushing.

### 7.3 Observation, not changed: the review tier on Keras 3 pickles

`getattr(keras.src.models.functional.Functional, '_unpickle_model')` is how Keras 3 pickles a model. It raised two MEDIUM review findings on
one file in 67. The review tier is working as designed ("unknown getattr name: look at it"); whether to add
this loader to the allow-list (the way `forward` is for YOLO) is a policy choice left open (the allow-list tier planned for 0.2). Adding it needs a failing test and
the real-data evidence above, and the allow-list rationale must say that loading the pickle still deserialises a Keras archive.

### 7.4 What I did not find

No test failure in task 1, no crash, hang, memory spike or unreadable file in 528 files (0 scan errors, 0 degraded), and the
second full pass reproduced every finding fingerprint of the first.
